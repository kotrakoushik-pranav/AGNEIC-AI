# Requirements Document

## Introduction

Aegis AI — Intelligent Emergency Response System is a professional command-center web dashboard designed for security operations teams monitoring a multi-camera facility. This first stage delivers the complete frontend dashboard with realistic mock data. The interface presents live camera feeds, incident tracking, system health, and a facility map in a premium, dark, cinematic design appropriate for SIH-level product demonstrations. No backend services, AI engines, authentication systems, or real-time data pipelines are implemented in this stage; all dynamic behavior is simulated via in-browser mock data and client-side timers.

## Glossary

- **Dashboard**: The single-page web application described in this document.
- **Operator**: A human user viewing and interacting with the Dashboard.
- **Incident**: A mock security or safety event generated by the client-side mock data layer, classified as CRITICAL, HIGH, or MEDIUM severity.
- **Camera Panel**: A UI component representing one monitored camera feed, rendered with a placeholder video frame and data overlays.
- **AI Overlay**: A mock bounding-box or label element rendered on a Camera Panel to simulate an AI detection result.
- **Incident Timeline**: A chronological list of event entries describing the lifecycle of a detected incident.
- **System Health Indicator**: A UI element reporting the operational status of a named subsystem.
- **Facility Map**: A dark, vector-style SVG map panel depicting a fictional building layout with camera and incident markers.
- **Mock Data Layer**: Client-side JavaScript that generates, updates, and provides all data consumed by the Dashboard without any external API calls.
- **Stat Card**: A compact panel in the Incident Overview section displaying a single numeric metric and its label.
- **Nav Sidebar**: The narrow vertical navigation panel on the left side of the Dashboard.
- **Top Header**: The compact horizontal bar spanning the top of the main content area.
- **Severity Badge**: A color-coded label indicating an Incident's severity (CRITICAL = red, HIGH = amber, MEDIUM = yellow).
- **Status Chip**: A small inline label indicating the current review state of an Incident (e.g., RESPONSE REQUIRED, UNDER REVIEW, MONITORING).

## Requirements

### Requirement 1: Application Shell and Layout

**User Story:** As an Operator, I want a stable, professionally structured page layout, so that I can navigate and read information without visual confusion.

#### Acceptance Criteria

1. THE Dashboard SHALL render a full-viewport dark layout consisting of a Nav Sidebar on the left, a Top Header spanning the top of the content area, and a scrollable main content region.
2. THE Dashboard root surface SHALL have a perceived luminance below 10%; panel surfaces SHALL have a perceived luminance between 8–15%, creating a visually distinct layering between the root background and panel backgrounds.
3. THE Dashboard SHALL apply a primary accent color such that the cyan/blue accent is the highest-chroma non-red/amber color used in all interactive and AI-status elements across the interface.
4. THE Dashboard SHALL apply red exclusively for CRITICAL severity indicators and amber/orange exclusively for WARNING/HIGH severity indicators throughout all components; no other component category SHALL use these colors for its primary indicator.
5. THE Dashboard SHALL use Inter or system-ui font at exactly 14 px base size, line-height 1.5, and letter-spacing normal for all body text.
6. AT 1280 px viewport width, THE Dashboard SHALL render all three regions — Nav Sidebar, Top Header, and main content — fully visible without a horizontal scrollbar appearing.
7. WHEN the viewport width drops below 1280 px, THE Dashboard SHALL ensure no content is clipped; a horizontal scrollbar SHALL appear on the main content region rather than breaking the layout.

### Requirement 2: Nav Sidebar

**User Story:** As an Operator, I want a persistent navigation sidebar, so that I can understand the system name and switch between sections at a glance.

#### Acceptance Criteria

1. THE Nav_Sidebar SHALL display the Aegis AI wordmark and a compact logo mark at the top.
2. THE Nav_Sidebar SHALL display a "SYSTEM ONLINE" status badge in green beneath the wordmark.
3. THE Nav_Sidebar SHALL contain navigation items in this order: Dashboard, Live Cameras, Incidents, Alerts, Analytics, Authorized Identity, System Health, Settings.
4. ON initial page load, THE Nav_Sidebar SHALL display "Dashboard" as the default active navigation item.
5. WHEN an Operator clicks a navigation item, THE Nav_Sidebar SHALL update the active item indicator to the clicked item without full page reload.
6. THE active navigation item SHALL have a left border of exactly 3 px solid cyan and a background opacity increase of 8–12% relative to inactive items.
7. WHEN an Operator hovers over an inactive navigation item, THE Nav_Sidebar SHALL apply a subtle background highlight transition within 150 ms.
8. WHEN the system status is not ONLINE, THE Nav_Sidebar SHALL display the status badge in red with the label "SYSTEM OFFLINE".
9. THE Nav_Sidebar SHALL display icons alongside each navigation label using a consistent icon set.
10. THE Nav_Sidebar SHALL remain fixed and not scroll with the main content area.

---

### Requirement 3: Top Header

**User Story:** As an Operator, I want a compact header showing key real-time metrics, so that I always have situational awareness without scrolling.

#### Acceptance Criteria

1. THE Top_Header SHALL display the page title "Emergency Command Center" as the largest text element within the Top Header region.
2. THE Top_Header SHALL display a "SYSTEM OPERATIONAL" status indicator with a green pulsing dot.
3. THE Top_Header SHALL display the count of active cameras using mock data (default: 4).
4. THE Top_Header SHALL display the count of active incidents using mock data; WHEN the Mock_Data_Layer changes the incident count, THE Top_Header SHALL reflect the updated count within 1 second without a page reload.
5. THE Top_Header SHALL display a notification bell icon with a red badge count matching the number of unacknowledged CRITICAL or HIGH Incidents; the badge SHALL be hidden when that count is zero. An Incident is considered "unacknowledged" when no Operator click or acknowledgement action has been recorded for it in the current session.
6. THE Top_Header SHALL display an operator profile area showing a placeholder avatar and the label "Operator / Admin".

---

### Requirement 4: Incident Overview Stats

**User Story:** As an Operator, I want a row of summary statistics, so that I can assess the current threat level at a glance.

#### Acceptance Criteria

1. THE Incident_Overview SHALL display exactly five Stat Cards with labels: "Active Incidents", "Critical", "Warnings", "Cameras Online", and "AI Confidence".
2. EACH Stat_Card SHALL display a numeric value sourced from the Mock Data Layer and a short descriptive label beneath it.
3. THE "Critical" Stat_Card SHALL render its value in red when the count is greater than zero.
4. THE "Warnings" Stat_Card SHALL render its value in amber when the count is greater than zero.
5. THE "AI Confidence" Stat_Card SHALL display a percentage value (e.g., "94%") in cyan.
6. THE Incident_Overview SHALL update displayed values to reflect changes from the Mock Data Layer without requiring a page reload.
7. WHEN an Operator hovers over a Stat_Card, THE Incident_Overview SHALL apply a subtle border highlight transition within 150 ms.

---

### Requirement 5: Live Monitoring Camera Grid

**User Story:** As an Operator, I want to see all camera feeds in a grid, so that I can monitor multiple locations simultaneously.

#### Acceptance Criteria

1. THE Camera_Grid SHALL display exactly four Camera Panels in a 2×2 responsive grid layout.
2. THE Camera Panels SHALL represent: CAM-01 Main Entrance, CAM-02 Parking Area, CAM-03 Building A Corridor, CAM-04 Restricted Zone.
3. EACH Camera_Panel SHALL render a placeholder video frame using a dark gradient or static image that visually resembles a CCTV feed.
4. EACH Camera_Panel SHALL display an overlay containing the camera ID, location name, a red "LIVE" indicator, and a running timestamp updated every second.
5. EACH Camera_Panel SHALL display an "AI ACTIVE" badge or label in cyan when the Mock Data Layer marks that camera as having active AI analysis.
6. EACH Camera_Panel SHALL display a mock person-count label (e.g., "3 persons detected") sourced from the Mock Data Layer.
7. WHERE the Mock Data Layer marks a camera as having an active Incident, THE Camera_Panel SHALL render a mock AI bounding-box overlay (a visible rectangular border with a label) to simulate an AI detection result.
8. WHEN an Operator hovers over a Camera_Panel, THE Camera_Grid SHALL apply a border highlight in the Incident's severity color (or cyan for normal) within 150 ms.
9. THE Camera_Panel for CAM-02 SHALL render a CRITICAL bounding-box overlay labeled "Possible Accident" with red border styling.
10. THE Camera_Panel for CAM-04 SHALL render a HIGH bounding-box overlay labeled "Restricted Entry" with amber border styling.

---

### Requirement 6: Active Incidents Panel

**User Story:** As an Operator, I want a structured list of active incidents, so that I can prioritize response actions.

#### Acceptance Criteria

1. THE Active_Incidents_Panel SHALL display a list of mock incidents provided by the Mock Data Layer, initially containing exactly three incidents.
2. EACH incident row SHALL display: incident title, location, camera ID, Severity Badge, AI confidence percentage, and Status Chip.
3. THE first incident SHALL have title "Possible Accident", location "Parking Area", camera "CAM-02", severity CRITICAL, confidence 94%, status "RESPONSE REQUIRED".
4. THE second incident SHALL have title "Restricted Area Entry", location "Building A", camera "CAM-04", severity HIGH, confidence 91%, status "UNDER REVIEW".
5. THE third incident SHALL have title "Crowd Density Warning", location "Main Entrance", camera "CAM-01", severity MEDIUM, confidence 87%, status "MONITORING".
6. EACH Severity_Badge SHALL use red background for CRITICAL, amber for HIGH, and yellow for MEDIUM.
7. EACH incident row SHALL display a timestamp indicating when the incident was first detected.
8. WHEN an Operator hovers over an incident row, THE Active_Incidents_Panel SHALL apply a subtle row highlight within 150 ms.
9. WHEN an Operator clicks an incident row, THE Active_Incidents_Panel SHALL visually mark that row as "selected" with a distinct left border accent.

---

### Requirement 7: Incident Timeline

**User Story:** As an Operator, I want a chronological event timeline, so that I can understand the sequence of events leading to and following an incident.

#### Acceptance Criteria

1. THE Incident_Timeline SHALL display a vertical list of time-stamped event entries.
2. THE Incident_Timeline SHALL contain at least five entries representing the lifecycle stages: AI Detection, Incident Classification, Location Verification, Alert Generated, Operator Acknowledgement.
3. EACH timeline entry SHALL display a timestamp, an event label, and a short description.
4. EACH timeline entry SHALL display a colored dot indicator: red for AI Detection and Alert events, cyan for AI Classification and Verification events, green for Acknowledgement events.
5. THE Incident_Timeline SHALL visually distinguish the most recent event using a brighter or highlighted dot relative to earlier entries.
6. THE Incident_Timeline SHALL render entries in reverse-chronological order with the most recent event at the top.

---

### Requirement 8: System Health Panel

**User Story:** As an Operator, I want to see the status of all system components, so that I know whether the monitoring infrastructure is operational.

#### Acceptance Criteria

1. THE System_Health_Panel SHALL display exactly six subsystem indicators with labels: "AI Engine", "Video Processing", "Backend", "Database", "Alert Service", "Camera Network".
2. THE "AI Engine" indicator SHALL display status "ONLINE" in green.
3. THE "Video Processing" indicator SHALL display status "ONLINE" in green.
4. THE "Backend" indicator SHALL display status "MOCK / DEV" in amber.
5. THE "Database" indicator SHALL display status "MOCK / DEV" in amber.
6. THE "Alert Service" indicator SHALL display status "MOCK / DEV" in amber.
7. THE "Camera Network" indicator SHALL display status "4/4 ONLINE" in green.
8. EACH subsystem indicator SHALL display a colored status dot (green for ONLINE, amber for MOCK/DEV) to the left of the label.

---

### Requirement 9: Facility Map Panel

**User Story:** As an Operator, I want a tactical facility map, so that I can spatially locate cameras and active incidents within the monitored site.

#### Acceptance Criteria

1. THE Facility_Map SHALL render entirely as an inline SVG or HTML Canvas element without any external map API calls or network requests.
2. THE Facility_Map SHALL depict a fictional multi-zone facility layout including at least: a Main Entrance zone, a Parking Area zone, a Building A Corridor zone, and a Restricted Zone.
3. THE Facility_Map zone backgrounds SHALL use colors with a perceived lightness between 15–25% on a 0–100% scale, consistent with the overall dark tactical design of the Dashboard.
4. THE Facility_Map SHALL render four camera markers, one per Camera Panel, placed in their corresponding facility zones.
5. THE Facility_Map SHALL render at least one active incident marker in the Parking Area zone with a red pulsing animation; the pulsing animation SHALL have a cycle duration between 1.5 s and 3 s.
6. WHEN an Operator hovers over a camera marker, THE Facility_Map SHALL display a tooltip showing the camera ID and location name.
7. WHEN an Operator moves the cursor away from a camera marker, THE Facility_Map tooltip SHALL disappear within 300 ms.
8. THE Facility_Map SHALL display a legend identifying camera markers and incident markers.

---

### Requirement 10: Mock Data Layer and Dynamic Updates

**User Story:** As an Operator, I want the interface to feel live and dynamic, so that the demonstration accurately represents how the system will behave with real data.

#### Acceptance Criteria

1. THE Mock_Data_Layer SHALL be implemented entirely in client-side JavaScript with no external API calls.
2. THE Mock_Data_Layer SHALL provide initial mock state for: incident list, camera statuses, person counts per camera, system health statuses, and timeline entries.
3. WHEN the Dashboard has been open for 30 seconds, THE Mock_Data_Layer SHALL update the "Operator Acknowledgement" timeline entry timestamp by adding exactly 30 seconds to its initial value.
4. THE Mock_Data_Layer SHALL update the per-camera person count values on a randomized interval between 10 and 20 seconds to simulate live sensor data.
5. THE Dashboard SHALL reflect Mock Data Layer updates in all consuming components (Camera Grid, Incident Overview Stats, Top Header) without requiring a page reload.
6. THE Mock_Data_Layer SHALL be implemented as a self-contained module; replacing it with a real API SHALL require no changes to any UI component file.

---

### Requirement 11: Interaction and Animation Quality

**User Story:** As an Operator, I want smooth, purposeful animations, so that the interface feels premium and responsive without being distracting.

#### Acceptance Criteria

1. THE Dashboard SHALL apply CSS transition durations of 150–300 ms for hover state changes on interactive elements.
2. THE "LIVE" indicator on each Camera_Panel SHALL display a red pulsing animation using CSS keyframes.
3. THE "SYSTEM OPERATIONAL" dot in the Top_Header SHALL display a continuous green pulsing animation.
4. THE active incident marker on the Facility_Map SHALL display a red pulsing ring animation.
5. THE Dashboard SHALL NOT use animations that loop continuously at high frequency (under 1 s cycle) on more than three elements simultaneously, to maintain a professional, non-distracting appearance.
6. WHEN an Operator clicks the notification bell in the Top_Header, THE Dashboard SHALL display a dropdown or modal showing the list of unacknowledged incidents.
7. WHEN the notification bell dropdown is open and there are no unacknowledged incidents, THE dropdown SHALL display an empty-state message (e.g., "No active alerts").
